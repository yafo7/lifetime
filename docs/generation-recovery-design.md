# 场景生成健壮性与分阶段恢复设计

日期：2026-10-15。本文保留实施前的代码调查与设计依据，下文“当前”指调查时的状态。后续已完成构建历史、服务端逐项空间检查点、手动修复／重验／发布，以及主屋入口吸附和建筑内部支撑层查询；实际使用与验证见 [场景自动生成](scene-generation.md) 和 [验证记录](verification.md)。更广泛的入口语义、岸线搜索、素材生成前的体型预检及局部 AI 意图修订仍是后续扩展。

## 1. 本次失败的实际情况

### 主屋门口：素材成功，空间装配失败

构建 `022db569-b244-4f2a-9558-e13f8d8ba01f` 的要求是“一名私家侦探从大门进入，绕着池塘，一直走到主屋的门口”。记录状态为 `assets-ready`，错误为“该点没有可行走表面”。

- 私家侦探演员 `ad602c27-7909-4834-8cfa-94f1f491ccf5` 已存在于 Actors。
- 模型版本 `4e9b855a-45e6-4478-877e-609f01e92a36` 已保存完整模型。
- 动画 `ec8d0c5c-4ac3-432b-bb4d-dfcfc8471792`，名称“侦探自然行走循环”，时长 2 秒，绑定上述模型版本。
- 两个素材任务均为 done，演员还没有保存完整动作。

使用实际地图、渲染地基几何和该模型计算的导航配置，只读重跑地点查询后：大门引导线与池塘环路解析成功；`hall_entry` 使用的引导线为 `[0,26] → [0,28]`，第二点失败。该引导线使用地图水平坐标；运行时对应的三维终点约为 `[0,0,28]`。

这个点附近实际 NavMesh 点为 `[0,0.03000003,27.6000061]`，水平距离约 0.40，超过 `Navigation.project()` 固定的 0.35 容差。只读计算中，吸附后的点可由引导线前一点及大门位置到达。

所以本例需要在地点求解阶段寻找并保存合适的附近站位。原始标记没有通过现有规则，并不说明主屋门前整体不可达；也不能通过扩大所有导航操作的容差来代替具体的候选选择。

### 凉亭中央：目录限制与实际可达性是两个问题

构建 `4cb8e388-1fc1-4fa8-851c-16de02e44ee0` 在规划阶段失败，尚未创建素材任务。

`semanticIndex.ts` 当前根据名称分类，只给 bridge 提供 center，building 全部只提供 near／facing。临波水榭因此无法在合法指导文档中表达“中央”。这是本地接口能力限制。

但只增加 center 枚举仍然不够：`LocationResolver.center()` 从模型上方发射射线，只取第一个命中表面，凉亭会先命中屋顶。只读检查显示中央 `[26,12]` 处存在约 0.60 高的地板，其 NavMesh 高度约 0.63；屋顶位于更高层。

进一步检查：在当前侦探通行配置（半径约 0.501、高度 2、台阶能力 0.3、坡度 35°）下，大门到这个中央站位返回 `TARGET_UNREACHABLE`。说明“有支撑面”“能站立”“能从起点走到”必须分别检查。本轮没有确定连接断开究竟由台阶、几何还是导航侵蚀造成，不能声称已经修好，也不能自动提高能力或将中央替换成亭旁。

## 2. 当前链路已经保留什么，缺少什么

| 产物 | 当前保存方式 | 当前缺口 |
| --- | --- | --- |
| 原始要求、基础演出、合法指导文档 | 服务端 `data/builds` | 非法规划响应只剩错误，缺少可修订的规划草稿 |
| 模型与动画 | 逐项写入 Actors，构建记录保存 manifest | 新构建会遮住旧构建的预览入口 |
| 收到但保存失败的生成结果 | 服务端结果缓存 | 现有重试语义应保留 |
| 已找到的地图 P 点 | 装配函数局部变量 | 任意后续失败时没有逐点检查点 |
| 已编译动作、已装配角色 | 整次装配返回后才保存 result | 后续角色或路径失败会丢失此次局部装配成果 |
| 全部装配成功但保存失败的结果 | 浏览器 localStorage 与 savedActions | 可续存，但不等于服务端空间草稿 |
| 正式演出 | 最后发布新版本 | 应继续保持完整校验，不直接存入不完整草稿 |

两个关键代码断点：

- `generationCoordinator.ts` 的 recover 只选 `list[0]`；服务端按创建时间倒序，新的凉亭规划失败会遮住较早的侦探构建。旧素材没有被删除。
- `buildCoordinator.ts` 只有 `await assembleScene(...)` 完整返回后才赋值 `record.result`；`performanceAssembler.ts` 中的地点、动作和角色都缺少逐项提交。

当前“继续原构建”有指导文档时不重调 chat，也不重生成 done 素材，但空间装配会从头再算。同一输入不变时，会重复同一失败。现有错误只保留一句话，无法定位到哪个角色、哪个位置或哪个状态转换。

## 3. 加强本地空间求解

### 3.1 分开地点含义、支撑面和通行能力

继续给 AI 小型摘要，不发送模型几何、NavMesh 或逐帧动画。摘要表达地点名称、类型、来源和可尝试的关系；本地记录具体候选与验证结果。

将“支持这一种查询”和“这次查询对这个角色可达”分开。规划可以表达合理的 center 意图，执行前由本地证明；候选缺失或不可达进入待修复状态。不能给所有建筑无条件声明“中央可进入”。

在实际需求出现的范围内补充入口关系及关联：建筑、入口、引导线的关系要显式可查。“门口”不能仅以建筑四周任一 near 点替代；“从大门进入”还涉及入口哪一侧和穿越方向。室内、门洞或亭心的候选来源应标明是地图标注、几何推断还是人工指定。

### 3.2 采用候选搜索，保留严格执行校验

地点求解按照以下顺序执行：

1. 从意图对应的局部区域获取多个候选，不因一个原始引导点失败就终止全部解析。
2. 获取候选位置上不同高度的支撑面，区分地形、地基、桥面、亭内地板和屋顶。
3. 检查坡度、角色净空、碰撞及水域，选择对应的 NavMesh 面。
4. 在语义允许的范围内做有限吸附，保存实际选中的位置和匹配的表面锚点。不能仍保存原始地形高度，或者使用属于另一表面的锚点。
5. 验证从前一站位是否可达，以及后续路线能否衔接。单点可站立不能替代整条行为可执行。
6. 按偏离目标程度、可达性、距离和空间余量排序；尝试少量候选组合。搜索有范围和次数上限。

`Navigation.project()` 继续承担严格的执行入口检查；新增或扩展的候选搜索负责“去哪里找”。吸附不能跨到另一层楼、墙另一侧或另一个不连通区域。

已有 `SurfacePicker.vertical()` 可以返回多个朝上的表面，`Navigation.nearest()` 提供有限范围查询，`Navigation.route()` 已检查完整路径。这些能力可以直接复用并补充语义约束，不必另建导航系统。

center 应在目标水平区域内寻找合适支撑层，并优先验证正确入口可达的内部站位。当前从顶部只取一个命中的办法需要替换。没有可达中央时，保留候选与原因供用户处理。

`alongGuide` 将地图引导线作为空间意图：保留必要转折和方向，各采样点允许有限投影；在障碍或局部失败位置细分采样，再连接实际导航路径。当前按索引抽样可能丢掉转折，不能继续假设引导线每一点都已适合角色站立。

`surroundingRoute` 优先使用水域边界附近的可走区域与已标注动线，检查闭合、环绕关系和水域避让。现有四个包围盒角点可以作为快速候选，但不能作为唯一策略。

### 3.3 把可行性检查提前

指导文档形成后，先检查地图要素、地点关系与明显空间问题。对未生成模型可以使用显式的预期体型做粗检查，结果标为暂定；模型完成后依据真实尺寸重验，动画完成后检查表演空间和状态衔接。

AI 继续提出意图。本地完成候选搜索、寻路和诊断；手动移动 P 点、重验路线不调用 chat。若确实需要改变意图，可单独提供一次有范围的重新规划：输入失败地点和可用选项，保留已生成素材与人工锁定点，不重跑整场素材生成。

## 4. 增加可恢复的构建草稿

复用 `SceneGenerationRun` 与 BuildJournal，在 `data/builds` 持久化独立的装配草稿。它可以不完整，因此不直接作为 Performance 保存。无需通用工作流框架。

建议记录：

- 构建、地图版本、基础演出快照、指导文档版本、草稿 revision。
- 稳定角色 key、位置 key、点 ID、动作 ID 和模型／动画资源引用。
- 每个位置的意图、有限候选、选择结果、自动基线、人工覆盖、锁定与验证状态。
- 每个动作、状态及状态转换的准备／校验结果。
- 结构化诊断：阶段、错误码、角色、地点、路径段、原因和可用处理方式。
- 已保存动作的真实版本、最终演出 ID、检查时使用的地图和角色通行配置。

未找到点时允许没有坐标，不能塞入 `[0,0,0]` 假装已定位。缺少起点的角色可以在素材预览中查看，不在地图中伪造一个有效出生位置。

合法产物与诊断逐项保存。某个地点失败后，继续计算不依赖它的地点、角色与素材；依赖失败节点的下游标记为等待修复。完成的素材一直属于 Actors，空间失败不撤销或隐藏它们。

阶段划分：

| 阶段 | 保存内容 | 失败后的操作 |
| --- | --- | --- |
| 意图规划 | 请求、合法方案；单独保留无效响应及诊断 | 修订地点意图，不把无效响应交给执行器 |
| 素材准备 | 模型、动画及 manifest | 查看已有素材，只重试确有失败的项 |
| 地点解析 | 每个位置的候选、已选 P 点、人工覆盖 | 定位问题点、拖点、选其他候选 |
| 动作装配 | 完整动作草稿、绑定和状态关系 | 修改依赖或继续装配 |
| 路线与表演验证 | 逐动作和转换的结果及失败位置 | 本地重新检查受影响部分 |
| 正式发布 | 已保存动作版本与完整演出 | 保存失败只续存，发布后打开新演出 |

状态区分待处理、计算中、通过、待修复和因上游修改而失效。空间问题不再只有回到 assets-ready 并附一条错误。

服务端提供受限的草稿读取、检查点写入与人工修改接口，沿用现有装配 lease，并加入 expectedRevision 防止多页覆盖。浏览器计算几何和 NavMesh；只向本地服务提交点位、意图和诊断，不持久化三角网格、派生路径或运行时钟。

检查点保存失败必须显示“尚未保存”，保留内存中成果；不能宣称刷新后一定恢复。原有 uncertain 远端任务语义继续保留，重试空间计算不会进入素材生成队列。

## 5. 增量重算与发布边界

| 用户改动 | 需要重算 | 应复用 |
| --- | --- | --- |
| 移动一个 P 点 | 该点、引用它的路线／动作及相关状态衔接 | 模型、动画、其他无依赖位置 |
| 修改通行能力 | 对应配置的导航、有关站位和路线 | 原始素材与人工点意图 |
| 替换同版本动画 | 引用它的完整动作及表演空间／时序检查 | 模型及无依赖动作 |
| 更换模型版本 | 该角色动画绑定、体型、路线和动作空间 | 其他角色与已保存原素材 |
| 地图资源版本变化 | 空间结果标为失效，基于新版本重新检查 | 模型、动画、指导意图；不直接发布旧检查结果 |

人工锁定点不会被自动重试覆盖，但仍要重新接受可达性检查。自动基线与人工覆盖分开记录，避免下次动作修改将手动修复误当成可丢弃候选。

构建中已独立通过的动作可以预览；未完成状态机不能显示为已可整体播放。正式发布仍要求本次方案所需角色、动作和衔接全部通过。若要只发布部分角色，必须成为一次明确的范围修改，而不是失败后自动删掉要求。

Actors 的完整动作可以逐项保存有效版本；地图点位仍只保存在 Play 构建／演出中。没有可执行动作的草稿不能伪装成 Actors 中已完成的动作。

## 6. UI 保持现有地图 → NPC → 状态／动作结构

地图或生成区增加次级“构建记录”入口，显示要求、时间与进度，能重新打开旧的待修复构建。正式演出版本与构建记录分别展示。

当前构建区域可以显示：

> 私家侦探：模型、行走动画已保存；主屋入口点待调整。
>
> 查看素材 · 定位并调整 · 重新检查

进入修复草稿后：

- 已有安全站位的角色静态显示，素材预览仍可用。
- 已确定的 P 点正常显示；有坐标但未通过的候选点带错误状态；无坐标的地点放入待放置列表。
- 选择动作后显示可计算的实际 NavMesh 路线；失败段标出原因，不用一条直线冒充可走路径。
- 拖动后只重新检查相关部分；提供“保存调整／取消调整”。保存目标是构建草稿，未通过也能保存以便继续修复。
- 全部必要检查通过后显示“完成并发布”，复用已生成素材形成新的正式演出。

复用当前 P 点拖拽与路线 overlay，但将读写目标改为可注入的构建草稿。不能直接调用现有 `savePath()`，因为它会写入正式演出。

## 7. 建议实施顺序与代码落点

1. **成果可见、错误可定位**：恢复构建历史选择；显示失败阶段和地点；确保 Actors 素材入口不受新失败影响。修改 generationCoordinator、sceneRequestPanel 及 workspace。
2. **服务端空间草稿和逐项检查点**：扩展 shared/sceneBuild、BuildJournal 与 builds/service；把 performanceAssembler 的一次性返回拆为地点、动作和验证的可保存步骤，改造 buildCoordinator。
3. **手动修复闭环**：在 Play 中打开草稿、拖点、显示实际路径、保存调整、只重算受影响部分，校验后发布。
4. **加强自动空间解算**：改进 semanticIndex、locationResolver 和 Navigation 的候选查询；先覆盖本次主屋门口与凉亭的真实失败，再扩展入口方向、环绕和多层表面。
5. **前置检查与受限意图修订**：减少晚期失败；验证素材无需重做的恢复链路后，再考虑增加一次局部 chat 修订能力。

建议先完成 1–3，立即让自动化失败能够被人工接住；4 与现有修复案例一起验收。上述模块均在现有 Actors／Play 架构内，不新增 NPC agent 或地图编辑器。

## 8. 验收案例

- 正式侦探素材可直接复用，主屋入口采用受约束的候选吸附后走完路径；修复过程中 chat／模型／动画请求数均为零。
- 凉亭可区分屋顶与地板；对当前不可达情况给出地点、候选和路线诊断，而不是仅说“不支持 center”。
- 第二个地点失败时第一个地点仍可见；第二个角色失败时第一个角色的成果仍可查看。
- 失败候选可拖动，未解析地点可手动放置；保存后刷新／重启仍能恢复。
- 新规划失败不遮住旧构建；有效素材能从 Actors 找到。
- 手动锁定点不被重试覆盖，变更点只使相关下游失效。
- 路径、点位有效性与状态衔接分别测试；不能把可站立误判成可到达。
- 多页面修改有版本冲突检查；旧演出和未涉及 NPC 不被草稿覆盖。
- 保存失败只续存；未知远端生成结果不自动重发；只有全部必要检查通过才能发布。

最初评审只进行了阅读、正式记录核查与只读空间计算。后续实施结果另记于验证文档，不将未实现的扩展视为现有能力。
